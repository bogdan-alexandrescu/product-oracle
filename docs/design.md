## Problem Statement

A founder-led company has no head of product. Product decisions happen ad hoc, the
company's knowledge is scattered across repositories, chat, docs and call transcripts,
PRDs and roadmaps take too long or never get written, and engineering builds things
that do not serve a company goal. Product Oracle acts as a very experienced head of
product: it builds a cited **baseline** linking company goals to products to features,
turns intake into a prioritized feature set, writes a **PRD** that iterates with the
founder's feedback until approved, and later produces an approved **roadmap** as HTML
and PDF. It is reachable through a web UI, a full REST API and an MCP server.

## Demand Evidence

- The owner named all four pains from their own company (F3 Why now): no one owns
  product, context is scattered, PRDs/roadmaps are too slow, and things got built
  that served no goal. Plus, in their words: "Product and Engineering need to
  communicate and align better on their roadmaps (engineering needs to support
  product and be super aligned)".
- Pushed to pick one (F3b Sharpest pain), they chose **built the wrong things**.
- The first user is the owner's own company: its next product version needs a PRD
  now, and the owner chose to run that PRD through an Oracle MVP rather than write
  it by hand. That is behaviour, not interest.
- Not yet evidenced: any outside company wanting this. Selling is explicitly later
  (F1 Customer: us first, sell later).

## Status Quo

Not asked directly. From F3 Why now: product work is ad hoc, the PRD and roadmap are
written slowly or not at all by people who also run the company, and engineering
plans drift from product intent. The workaround Oracle must beat is a founder
writing the PRD alone from memory plus a few searches.

## Target User & Narrowest Wedge

- **User (F2 Primary user):** a founder/CEO with no head of product. Oracle is the
  head of product: opinionated, makes the call, shows its reasoning; the founder
  approves or overrides.
- **Wedge (F4 v1 scope):** baseline + PRD feedback loop. The roadmap follows in v1.1.
- **v1 quality bar (F3b Sharpest pain):** goal traceability. Every proposed feature
  traces to a company goal with citations; anything serving no goal is flagged and
  sinks. Test: replay last quarter's features and check Oracle flags the regretted ones.

## Constraints

- Agents run on **SwarmCloud** (P2 Agent runtime), which today cannot attach an MCP
  server or secret to a task, clones one repo per workflow, fixes the model per
  profile, and cannot pause a workflow for a person. Four requests are filed:
  #1433, #1434, #1435, #1436 (X2 SwarmCloud gaps, X4b Public filing).
- Hosting on existing GKE + Cloud SQL Postgres (pgvector) + GCS, gitops deploys
  (P1 Hosting).
- Python (FastAPI, async SQLAlchemy, Alembic) + Next.js/Tailwind, standalone repo
  (P4 Stack, P4b Repo location). The repo is **public** (R0 Repo visibility), so no
  company or customer data is ever committed; it lives in a gitignored `private/`.
- Claude models only; every run shows a cost estimate, runs over $50 wait for
  approval, overrun past 1.5x the estimate pauses and asks (P3 Cost policy).
- Multi-tenant data model (tenant_id on every table) from day one, single tenant in
  practice; signup, billing and SOC 2 deferred (F1 Customer).

## Premises

1. Traceability beats prose: a PRD is only as good as the goal-to-feature links under
   it, so the baseline is a correctable, cited graph, not document search
   (B1 Baseline shape).
2. Oracle is the control plane, SwarmCloud the execution plane. Oracle owns state,
   knowledge, documents and approvals; SwarmCloud runs the agents (P2, X1).
3. Agents read Oracle's knowledge through Oracle's own MCP server with a run-scoped,
   expiring token; data never leaves Oracle (X1 Knowledge access).
4. Oracle is the PRD's source of truth; exports are snapshots (O1b PRD home).
5. The founder decides. Oracle pushes back once with evidence, then complies and logs
   the override (C1b Pushback policy).

## Approaches Considered

### Agent runtime (P2)
- **Chosen: SwarmCloud as runtime.** Dogfoods the owner's own agent platform; Oracle
  becomes its first serious product customer. Cost: Oracle v1 depends on four
  SwarmCloud features.
- Ruled out: Agent SDK orchestrator in-app (owner chose SwarmCloud); Claude Managed
  Agents (vendor dependence, data leaves infra); Temporal + raw API (another system,
  own agent loop).

### Agent knowledge access (X1)
- **Chosen: Oracle MCP + run token.** Ruled out: per-product workspace git repo
  (chat/transcripts in git history forever); context pasted into prompts (agents
  can't look beyond what Oracle guessed).

### First release shape
- **Chosen: two parallel tracks.** The first dogfood PRD is produced by an agent
  pipeline run from this folder that never waits on the app; a thin app is built
  alongside it, imports the drafts, and takes over the feedback loop once it is up
  ([`docs/mvp-app.md`](mvp-app.md)). Ruled out: app-only (the PRD would wait on
  plumbing); agents-only (no product to show for it).

## Recommended Approach

### Architecture

```
            ┌───────────── Product Oracle (GKE) ─────────────┐
 founder ─▶ │ web (Next.js)  ──▶  api (FastAPI: REST + MCP)  │
 API/MCP ─▶ │                      │        ▲                │
 clients    │ workers: connector sync, pipeline orchestrator │
            │ Postgres+pgvector (graph, docs, runs)  GCS     │
            └──────────────┬───────────────▲─────────────────┘
                           │ workflows     │ MCP (run token)
                           ▼               │
                    SwarmCloud: indexer / claude-code / -sonnet / -haiku
                    steps, await_input checkpoints (#1436)
```

- **Knowledge:** connectors sync sources incrementally (webhooks + polling); each run
  pins the snapshot it started on and offers a refresh between drafts (S4 Freshness).
  Admins allowlist channels, spaces, repos and folders; DMs are never ingested;
  source ACL metadata is stored for per-user mirroring before selling (S3 Visibility).
  Connectors use each tool's API integration, on one admin's credentials for now
  (S5 Connector auth).
- **Code understanding:** one SwarmCloud `indexer` task per repo builds a capability
  map (modules, APIs, data models, flags, jobs) plus issues, PRs, milestones and
  releases; refreshed on merge (S2 GitHub depth).
- **Baseline graph (B1):** typed entities (Goal, Product, Feature, Requirement,
  Constraint, Decision, Person, Evidence) and edges (supports, depends_on, blocks,
  evidenced_by). User corrections are locked; agents must ask to override. Goals are
  extracted from every source, proposed in measurable form and confirmed, with a goals
  interview where gaps remain; horizons default to current quarter / next 2 quarters /
  12–24 months (B2 Company goals). Every claim cites; conflicts resolve by stated
  precedence (code > tracker > docs > chat, newer beats older) and escalate only when
  they change a decision (B3 Conflicts).
- **Pipelines (W1):** three built-in flows as code-defined templates with knobs
  (depth, agent roles, checkpoints, budget): Baseline -> PRD, Feedback loop, Roadmap.
  Custom flows via API specs in v2; no visual builder.
- **Checkpoints (W2):** baseline confirm, feature set + dependencies, priority order,
  PRD review, plus an eng review stop (E1); each toggleable when a flow starts, all on
  by default, each one approver per stop (C2 Approvals). Each is a SwarmCloud
  `await_input` step once #1436 lands; until then Oracle runs one workflow per segment
  between checkpoints. Approving the feature set approves the **PRD scope**: the
  checked `feature_set.yaml` (every feature traces to a confirmed goal or is flagged;
  blocking problems disable Approve) becomes the features and requirements this PRD
  includes, excludes or defers, and the priority order, the PRD draft and the
  document's next drafts read that scope, not the whole baseline (C6). The priority
  order's `priority.yaml` is checked the same way (every included feature ranked once,
  after the features it depends on; blocking problems disable Approve) and compared with
  Oracle's live ranking on the Priorities screen; approving the stop saves it as this
  PRD's priority snapshot, which the roadmap reads (C8).
- **Outputs:** PRD with multiple versioned templates (O1); feature design = stories,
  acceptance criteria, SVG flow, low-fi HTML wireframes, with hi-fi mockups and
  clickable prototypes opt-in in v2 (O2); goal-weighted prioritization by default,
  RICE / MoSCoW / WSJF selectable (O3); roadmap Now / Next / Later with dated
  milestones only in Now, switchable to quarterly or outcome views (O4); branded
  HTML/PDF, expiring share links, audience variants, public links via a public-safe
  variant (O5); SVG diagrams, engineering inputs, and Figma frames via Figma's MCP
  `use_figma` (beta, needs #1433) (O6).
- **Engineering alignment (E1):** approved PRD -> epics + issues in the tracker; read
  back status, estimates and plan; flag drift both ways; tech brief per feature from
  the code map; weekly read-only alignment report.
- **Feedback (C1, C3):** inline comments on selections, per-section approve / reject /
  request changes, chat that turns discussion into feedback items, Slack pings and
  thread replies; every version kept, any-two-version diff, and a per-version report
  of how each item was addressed.
- **UX (I4):** a workspace (Baseline, Runs, PRDs, Roadmap, Inbox) with a
  head-of-product chat docked beside every screen.

## Success Criteria

- Traceability: 100% of features in an approved PRD link to at least one confirmed
  goal with at least one citation; features serving no goal are flagged.
- Replay test (F3b): on last quarter's shipped features, Oracle flags the ones the
  founder now regrets.
- Speed: intake to approved PRD in hours, in three or fewer feedback rounds.
- Engineering alignment: the eng lead's review finds no "that's not how it works"
  claims; the alignment report shows drift both ways.
- MVP: the first dogfood PRD is approved with its last feedback round run through the
  thin app.

## Distribution Plan

A web service. MVP runs from `docker compose` on the owner's machine (assumed; see
`mvp-app.md`). v1 deploys to the existing GKE cluster through the gitops flow;
CI on GitHub Actions (lint, tests, build, image push).

## Dependencies

- SwarmCloud #1433 (per-task MCP + ephemeral credential) blocks agents reading Oracle;
  #1434 (extra read-only repos), #1435 (model-tier profiles), #1436 (`await_input`)
  have workarounds.
- Figma's MCP write tool is in beta and will become usage-priced.
- Connector credentials: one admin's personal Notion/Fireflies/etc. access for now.
- Existing GKE, Cloud SQL and gitops infrastructure.

## The Assignment

Before the first baseline checkpoint, write down your company's 3–5 goals for the
next two quarters, each with one measurable target and an owner. Oracle traces every
feature to a goal; if the goals are vague or unwritten, the traceability bar fails on
day one, however good the agents are.
