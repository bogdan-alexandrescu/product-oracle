# Product Oracle MVP — thin app spec

Status: DRAFT — owner approval pending. Parent design: [`docs/design.md`](design.md).

## Purpose

The first dogfood PRD is produced by an **agent track** (agents run from a local
folder, reading sources and writing PRD drafts as markdown). That track never waits
on this app. The thin app's job is to **take over the PRD feedback loop**: import each
draft as version N, let the founder review it (inline comments, per-section verdicts),
hand the open feedback back to the agent track, show diffs between versions, approve,
and export HTML/PDF.

Budget: about 1.5 days of work by parallel agent lanes. Two milestones:

- **M-A, import + review:** a draft can be imported, rendered, commented on, reviewed
  per section, and its feedback package pulled by the agent track.
- **M-B, full loop:** version N+1 imports with resolutions, diff works, a version can
  be approved and exported to HTML and PDF.

## In scope

- Import a PRD draft (markdown with section ids, citations, optional resolutions) as
  version N of a document.
- Render a version: sections, citation chips with source links and excerpts.
- Inline comments on text selections, with replies and resolve.
- Per-section verdicts: approved / changes requested / rejected, with a note.
  Approved sections are reported as **locked** to the agent track.
- Feedback items: one list of every comment and section verdict, with status
  (open / addressed / declined / superseded) and the version that addressed it.
- Resolution report per version: how each feedback item was handled (C3 Version
  history).
- Diff between any two versions: section-level (added / removed / changed / moved)
  plus word-level inside changed sections.
- Approve a version (document status `approved`).
- Export a version to HTML, PDF and markdown, with a version banner.
- REST API (OpenAPI generated by FastAPI) for everything above, so the agent track can
  push drafts and pull feedback without the UI.
- Auth: one admin user (UI session cookie) plus API tokens for the agent track.
- `tenant_id` on every table from day one; a single seeded tenant.

## Cut from the MVP

## Draft import format

One markdown file per version. YAML front matter, then the body.

```markdown
---
document: checkout-redesign          # slug; created on first import
title: Checkout redesign PRD
template: oracle-default             # optional
template_version: "1"                # optional
snapshot: 2026-10-16T14:00Z          # optional source snapshot label
brief: [summary, goal-trace]         # optional: the brief layer's section ids (O1f)
citations:
  - id: c1
    source: slack                    # slack | notion | gdocs | github | fireflies | upload | web | oracle
    ref: https://example.slack.com/archives/C123/p1700000000
    title: "#product thread on drop-off"
    excerpt: "Most users abandon at the shipping step"
    retrieved_at: 2026-10-16T13:10Z
    item: 3f1c2a4e-...               # optional: the source item read
    confidence: 0.75                 # optional: a number from 0 to 1, or null
    confidence_note: "two sources agree; fresh"   # optional: how it was reached, or why none
    low_confidence: false            # optional: under the company's low threshold
resolutions:                         # optional: how this version handled earlier feedback
  - feedback_id: 0b8c...             # id from the feedback package
    status: addressed                # addressed | declined
    note: "Ranked by installs, see §5.2"
---

# Checkout redesign PRD {#title}

## 1. Goal trace {#goal-trace}
Serves G1 (activation) ... [c:c1]

## 5.2 Shipping step {#s-5-2}
...
```

Rules:
- Every heading of level 1–3 must end with `{#section-id}`; ids are unique within a
  version and stable across versions (that is what makes diffs and locks work).
- Inline citations are `[c:<id>]`; every id used must exist in `citations`, and
  unknown ids fail the import with a 422 listing them.
- The citation contract agents read (`oracle.docs.schemas.citation_contract`, in the draft
  prompts and `push_draft`): `source` is one of the kinds above (`oracle` for Oracle's own
  baseline, its `ref` the item's kind and key, e.g. `baseline decision <key>`), and
  `confidence` is a number from 0 to 1 or null (migration `0019_citation_confidence`
  stores it under the same check). Any other source or confidence fails the import:
  "citation #1 (c1) is invalid: confidence must be a number from 0 to 1".
- Same content hash as an existing version: return that version (200), no duplicate.
- `resolutions` are applied on import: each referenced feedback item gets its status,
  note and `addressed_in_version`.
- If a section that was **approved** in the previous version changes, the import
  succeeds but the version carries a `locked_section_changed` warning listing ids.
- Brief layer (O1f, see `docs/brief-and-full.md`): the sections named in `brief`, else
  the template version's `brief` markers, else the sections before a level-1
  `# Full version {#full}` heading; unknown ids in `brief` fail the import.

## Data model

All tables: `id uuid pk`, `tenant_id uuid not null` (indexed, FK tenants),
`created_at timestamptz`. Every query goes through a tenant-scoped session helper.

| Table | Key columns |
|-------|-------------|
| `tenants` | `name` |
| `users` | `email` (unique per tenant), `password_hash`, `role` (`owner`) |
| `api_tokens` | `name`, `token_hash`, `last_used_at`, `revoked_at` |
| `documents` | `slug` (unique per tenant), `title`, `status` (`draft`/`in_review`/`approved`), `template`, `template_version`, `updated_at` |
| `document_versions` | `document_id`, `number` (unique per document), `markdown`, `content_hash` (unique per document), `front_matter jsonb`, `snapshot`, `warnings jsonb`, `imported_by` (user or token id), `approved_at`, `brief_source` (`draft`/`template`/`full_heading`/`none`) |
| `sections` | `version_id`, `section_key` (unique per version), `ordinal`, `level`, `heading`, `body_md`, `body_text`, `content_hash`, `citation_keys text[]`, `layer` (`brief`/`detail`) |
| `citations` | `version_id`, `cite_key` (unique per version), `source`, `ref`, `title`, `excerpt`, `retrieved_at` |
| `comments` | `version_id`, `section_key`, `anchor jsonb` (`{exact, prefix, suffix}`, W3C TextQuoteSelector), `body`, `author_id`, `parent_id`, `resolved_at` |
| `section_reviews` | `version_id`, `section_key`, `verdict` (`approved`/`changes_requested`/`rejected`), `note`, `reviewer_id` (history kept; latest per section wins) |
| `feedback_items` | `document_id`, `raised_on_version`, `kind` (`comment`/`section_review`/`general`), `comment_id`, `section_review_id`, `section_key`, `summary`, `status` (`open`/`addressed`/`declined`/`superseded`), `addressed_in_version`, `resolution_note`, `updated_at` |
| `audit_events` | `actor`, `action`, `entity`, `entity_id`, `data jsonb` |

Creating a comment or a non-approved verdict creates an `open` feedback item; a later
verdict on the same section supersedes the earlier item.

## Roadmap item talk and action cards (roadmap-talk)

- **The card's talk.** On `/simple/roadmap` an item's card has **Talk to Oracle**. It widens the card in place: the details on the left, the talk on the right, headed "Talk about <code> <title>", with **Hide the talk**. Under the message box: "Just you and Oracle · kept with this item". On a phone the bottom sheet has two tabs, **Details** and **Talk to Oracle**. The talk uses the Ask chat endpoints with the page `/simple/roadmap/items/<item id>`, so there is one thread per item and person. In it, "it" and "this" mean the item. Oracle's answers can carry a `source` line, for example "From the PRD · F-16 Adaptive pacing".
- **Action cards.** Oracle restates each change ("I understood: move … two weeks later, to Nov 30 – Dec 11, 2026.") and adds one card per change: moving dates, moving to another milestone, adding an item, splitting an item, setting the owner, renaming or cutting it. A card shows **Before → After** (`change_words`) and its red reasons. A card with `correct` has **Apply** (**Propose** for commenters and approvers), **Reject** and **Correct**. Correct opens the card's fields (Title, Goal, Milestone, Start, End, Owner), filled in with Oracle's reading. Apply then sends `{values}`, the server rebuilds the card from them, and the restatement updates. Viewers get a note and no cards.
- **After Apply.** The item's bar flashes on the timeline for about 2.5 s (`simple:applied`), and the roadmap reloads (`simple:card-changed`). The same cards show in the roadmap's Ask panel. A line with two or more open cards keeps **Apply all**.
