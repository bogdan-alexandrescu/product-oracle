# Screen 1 · Composition inspector (`composition`)

Reached from a PRD (nav "prds"). Example: "Team workspaces" `team-workspaces`, template `oracle-default` v3,
pack General Tech Startup (packs_source default); rev 3 confirmed, rev 4 a working draft that adds
`platform.tenant-isolation`, rev 2 published, rev 1 superseded. Catalog = the 9 mock modules.

## A · Module table + inspector (`1-composition-a.html`, as approver)
- Idea: the Plan pattern. Modules table grouped Mandatory / Suggested / Optional (order, key, selection, decided_by,
  brief/full section counts, version), filter chips, 380 px inspector for the selected module, a "Working draft"
  panel below with the diff against the confirmed revision and the required reason. Catalog, Company policy and
  History are tabs (rendered small on the board).
- Trades off: the revision story (diff, outline) is secondary; best for "why is this module here?".
- Shows: selection, included, decided_by, policy_source, reason, explanation, basis (path/op/expected/actual/holds/
  missing/knowledge_state/evidence_ids/source), questions + missing_information, layer_impact, depends_on/required_by/
  conflicts_with, version/latest_version/upgrade_available, score (labelled advisory), field_problems, condition_error,
  sections.unmapped, required_review_role, revisions[], seg working vs current.
- States: legacy + recommendation, loading, empty filter, 409 stale, 422 required_module / required_dependency,
  non-fatal decision_superseded, publish 409, owner vs approver on an owner-review module (disabled + "Requires the owner
  role"), viewer/commenter read + preview; policy-changed flag notice.

## B · Revision-centric (`1-composition-b.html`, as approver)
- Idea: the page is "the change you are about to make". Left: revision timeline (status, decided_by/at, reason,
  parent). Centre: diff of draft vs revision in force (added / removed / version_changed / reordered / material /
  affected_sections) and the PRD outline after confirm in Brief | Full columns (recommend `outline[]`: heading, level,
  layer, module, origin; new sections highlighted, unmapped kept). Right: confirm inspector with changes
  (add/remove/order), preview problems and missing info, status seg confirmed vs working, reason, base = head.
- Trades off: weak for browsing per-module reasoning (basis, questions); strong for the "material change invalidates
  approvals" and "never last-write-wins" rules.
- Phone: timeline becomes a deliberately scrolling revision strip; confirm form opens as a sheet.
- States: no draft, legacy, loading preview, reorder-only (not material), 409 stale, 422 role_required / conflict /
  order_violation / missing reason, decision_dropped after confirm, the three publish 409 messages, owner, viewer.

## C · Policy-first board (`1-composition-c.html`, as owner)
- Idea: company module policy as four lanes (Required / Optional / Disabled / Follows pack) of catalog cards, default
  packs (max 10) on top, inspector = catalog entry (description, company_policy seg, applies_to, depends_on,
  conflicts_with, section_ids, brief/full layer, required_review_role, versions with origin/contract_hash/created_by,
  `contract`). Each card says what it means for the PRD you came from.
- Trades off: an owner tool, not the per-PRD inspector; approvers and viewers see it read only. Moving cards has no
  drag (seg "Move to" in the inspector).
- States: saved (flags compositions, re-confirm to apply), is_default, loading, empty pack filter, 422 policy_overlap /
  unknown_module / unknown_pack, 10-pack limit, archived module, approver read only, 403 "Requires the owner role",
  viewer, and the Template manifest tab (module_key, version, policy, display_order, unmapped_sections).

## Pick
A as the composition screen, it answers every §4.5 item in one place and matches Plan. Take from B the diff + Brief/Full
outline for the Confirm dialog (it is the clearest way to show material impact before confirming), and use C as the
Company policy tab for owners.
