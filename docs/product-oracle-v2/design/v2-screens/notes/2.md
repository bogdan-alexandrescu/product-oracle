# Screen 2 · Impact explorer and targeted regeneration plan (`impact`)

Source: `GET /v1/documents/{doc}/versions/{n}/impact` (preview), `/v1/baseline/entities/{id}/impact` (what-if),
`/v1/trace/changes/{id}/impact` (recorded). All return ImpactReport. Per-row acting: `POST /v1/trace/staleness/actions`,
then `POST /v1/spec-requests/{id}/regenerate` (specs/design) or `/v1/documents/{doc}/regenerate/estimate` + `/regenerate` (roadmaps).
No route runs a whole plan, so no direction has a "run all" button. Closest existing pattern: `web/components/SpecStaleness.tsx`.

## A · Table + inspector + plan list (`2-impact-a.html`)
- `affected` in a DataTable grouped by `category`, with the first reason as a subline. The inspector shows the selected
  TraceOutput's `dependencies` (freshness, upstream `document_slug` vN · `section_key`, `stale_since`, `caused_by_change_id`),
  `reasons`, the proposal's `how`, and the per-row actions (review / accept_regeneration / reconcile, then Propose regeneration).
- Below the table: the `plan` as a numbered list (action chip, `section_keys`, `how`), the superseded row shown as "No proposal",
  and `affected_entities` (key, type·status, confidence, locked).
- Trade-off: closest to the Plan/Decisions pages and the cheapest to build. "Why" is shown as text only, and the plan sits apart from the table.
- Board: empty, loading, 404, recorded change (ChangeEventOut), what-if entity subject, truncated, deleted upstream, four freshness values,
  "review" row, 422/409, regenerate result (`run_id`, `dropped_section_keys`), roadmap estimate over threshold, owner, 403, viewer, commenter-decider.

## B · Lineage graph + plan sidebar (`2-impact-b.html`)
- Left to right: subject → changed sections and baseline items (from dependency `upstream.section_key` / `upstream.entity`) → outputs
  ordered stalest first. Selecting an output highlights its path. Deleted upstreams get dashed red edges.
- The sidebar is the plan: count stats (`counts.total`, plan length, `counts.approved`), with the selected proposal expanded with its actions.
- Trade-off: shows *why* an output is affected best, and a deleted section stands out. It is the most work to build (layout code for the edges),
  gets messy past about 15 outputs or near `truncated` limits, and on a phone it falls back to a grouped list.
- Board: same coverage as A, drawn as nodes and plan rows.

## C · Plan-first document (`2-impact-c.html`)
- The page is the plan: summary (affected / proposals / approved kept / not in plan), then one step card per RegenerationProposal
  with `how` as the main text, `section_keys`, and a 3-stage strip per row: settle staleness → propose draft run
  (spec: `run_id`, `prd_version`, sections) or estimate (roadmap: `estimate_usd` vs `approval_threshold_usd`, `needs_owner_approval`)
  → estimate and start on the run page / start the roadmap run.
- The aside shows what changed (sections with output counts, `affected_entities`, per-category counts).
- Trade-off: best for "get this done" and the only one that shows the cost and approval path for each row. It hides the dependency
  detail (per-dependency freshness and stale_since) and is weaker as a browse/explore view. The 3 stages are just the order the UI
  suggests; the API does not need accept_regeneration before regenerate.

## Recommendation
**A as the base, with C's per-row stage strip in the inspector's action section.** A shows every ImpactReport field with existing
components (DataTable, Inspector) and matches how SpecStaleness and the Plan inspector already act on staleness. C's stage strip adds the
cost and approval path that A's footer leaves implicit. Keep B's lineage for a later "Why" tab if teams need it.

Shared-class requests: none (all screen CSS is in each file's style block).
