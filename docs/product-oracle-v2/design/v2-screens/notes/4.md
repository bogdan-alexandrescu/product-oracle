# Screen 4 · design (low-fi wireframes and user flows of a spec)

Reached from a spec's tech brief (nav PRDs). Artifacts are found through `SpecOut.design[]`;
each page is `GET /v1/design-artifacts/{version_id}`, files shown from `outputs/{name}` in a
sandboxed iframe (drawn inline as grayscale markup in the mockups). Annotation numbers are
the ones Oracle's sanitiser writes into each wireframe's footer ("1. id [section]"); the UI
cannot place pins over a sandboxed, script-free iframe, so no direction overlays pins.

## A · Canvas + review inspector (`4-design-a.html`, as approver)
- Idea: one artifact version per page (strip switches between the spec's flow and wireframes); the selected file large in a framed canvas, the 380 px inspector holds verdicts, numbered annotations with their threads, version reviews and version meta.
- Trades: one file at a time; comparing wireframe screens means switching the output segment.
- Shows: title, kind, version number/status/freshness, stale reason + tech brief link (Approve disabled), outputs name/title/media_type/size/sha256/section_keys/requirement_ids, annotations id/target/note/section/requirements/reviews, review events (comment, marked_stale), summary, provenance (run_id, prd_version, prompt_version, runner_profile, requirement_ids), composition_revision, content_hash, created_at, lineage freshness.

## B · Filmstrip / compare (`4-design-b.html`, as owner)
- Idea: the whole spec's design on one page: thumbnails of every output, the flow full width, wireframe screens side by side with their footer labels, one verdict bar per version, one review timeline table (grouped by version) with a comment composer that targets the version or one annotation.
- Trades: best for "does the set hang together"; long page, thread per annotation is only visible in the timeline; it composes two `GET design-artifacts` calls.
- Shows: both artifacts' status/freshness, removed[] (Sanitised chip + notice), annotations with comment counts, event kinds (comment, marked_stale, changes_requested) with data.output/annotation_id, verdict rules (Approve off when stale; note required).

## C · Annotation checklist (`4-design-c.html`, as commenter)
- Idea: each annotation is a row to discuss, grouped by file; progress "3 of 4 discussed" (annotations with at least one review); the inspector shows the file with that annotation's label, its thread and a composer; version-level discussion and meta below the table.
- Trades: strongest for structured review of many annotations (up to 30 per file); the artifact is secondary (small, in the inspector); weaker for judging a flow as a whole.
- Shows: annotation id/note/section_key/requirement_ids/reviews, removed[], version reviews (comment, changes_requested), commenter role (verdicts disabled, named engineering approvers listed), provenance, content_hash.

Every file's board covers: loading, 404 "design artifact version not found", 404 "output 'cart-3.html' not found", sanitised removed[], regeneration running (SpecOut.regeneration_run_id), approved (approved_by/approved_at), superseded/rejected read only (409 "version 1 is rejected"), 409 stale approve message, 422 "say why: a note is required to request changes or reject", 422 "a comment needs a body", 422 "a verdict is on the version...", no reviews yet, annotation with no reviews, viewer / commenter / approver not named (403) / owner.

## Recommendation
A. It matches the app's split + inspector pattern, gives the artifact the space a reviewer needs, and keeps the API's unit (one version, one verdict) on screen with the stale gate right next to Approve. Borrow C's "annotations with no comments" filter into A's inspector, and B's side-by-side mode as an option when a wireframe version has 2-4 screens.
